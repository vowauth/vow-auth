# Разбор по тестам: как работает, узкие места, пробелы

Дата: 2026-10-25, ветка `proto/v1`.

Метод: прочитаны все 50 тестовых файлов, контракты `packages/store-contracts`, карта `examples/flow-map` и документация. Код библиотеки не читался. Подозрения из раздела 2 проверены отдельным временным тестом через публичный API `createAuth`; в репозиторий этот тест не попал.

## 1. Как всё работает

### Вход (`auth.signIn`)

1. Проверка `tenant` и `device`: непустой текст без управляющих символов и одиночных суррогатов. Иначе `invalid-request`, ни одно хранилище не вызывалось.
2. Фактор (плагин) проверяет ответ. Ядро принимает от него закрытую форму: `provider`, `externalId`, `email`, `emailVerified`. Почта канонизируется (NFKC, нижний регистр, punycode, лимиты RFC 5321). Результат — замороженный `Proof`; объект той же формы, но не выпущенный `verifyProof`, отвергается.
3. Субъект ищется по `(provider, externalId)`. Если не найден и почта подтверждена — идентичность привязывается к владельцу этой почты (самая ранняя идентичность, подтвердившая адрес). Иначе создаётся новый субъект. Всё атомарно, «первый выигрывает».
4. При подтверждённой почте ядро само вызывает `confirm-email`: у остальных заявителей этой почты отзываются сессии, их неподтверждённые претензии снимаются, опустевшие субъекты помечаются вытесненными.
5. Политика. Разрешение — только строка `"allow"`; `requireFactor(id)` просит второй фактор; всё остальное, включая исключение, — отказ.
6. Токен сессии: AES-GCM, ключ из HKDF с целью `session`. Внутри цепочка «тенант → пользователь → устройство → сессия» со штампами эпох, методы и время входа.

### Step-up

Продолжение — одноразовая запись, привязанная к тенанту, устройству и запрошенному фактору. Первая попытка её сжигает, даже ошибочная. Второй фактор должен принадлежать тому же субъекту и ничего не создаёт. TOTP работает только вторым шагом и получает субъекта от ядра, а не от клиента.

### Сессии и отзыв

Проверка — ровно одно чтение хранилища эпох; сроки считаются по его часам. Отзыв поднимает штамп уровня до `max(текущий + 1, now)`; умирают все токены, выданные до отзыва. Ключ отзыва живёт максимальный срок токена.

### Агенты

Делегирование выдаётся по живой сессии. Цепочка из 4 звеньев (тенант, человек, агент, делегирование) или из 6 (плюс устройство и сессия). Токен агента не годится как сессия и наоборот, делегировать дальше нельзя. Права хранит приложение, `narrow` может только добавлять запреты.

### Остальное

- Одноразовые токены: в хранилище только SHA-256, атомарный `take`, неверная цель сжигает токен, отказ одинаковый, причина только в аудите.
- Счётчик: скользящее окно, отказанный запрос ничего не считает, режим `observe` для выкатки лимита.
- Outbox: доставка минимум один раз, аренда, `attempts`, закапывание после предела.
- Аудит обязателен. Расширяющие доступ решения пишутся до действия, и упавший приёмник их блокирует. Отзыв выполняется и при упавшем приёмнике, но ошибка доходит до вызывающего.
- HTTP: для браузера cookie `__Host-` (HttpOnly, Secure), проверка Fetch Metadata и Origin, только JSON; для Bearer токен в теле, CORS по точному списку, `device` не короче 16 знаков.
- Сервис: общий секрет, ответы `no-store`; любой сбой сети — отказ `unavailable`, никогда не успех; повторов нет.

## 2. Подтверждённые проблемы

**P1. Пользователь, которому провайдер позже подтвердил почту, больше не войдёт.** Первый вход Google с `emailVerified: false` проходит. Следующий вход той же идентичности с `true` получает `forbidden` — и так навсегда. Похоже, исход `existing` не обновляет хранимую идентичность, а `confirm-email` не находит субъекта владельцем почты. Тестов на это нет.

**P2. Пользователь, сменивший почту у провайдера, тоже заблокирован.** Та же идентичность с новой подтверждённой почтой получает `forbidden`; владельцем старой почты остаётся прежний субъект. Обновление claims при повторном входе не покрыто вообще.

**P3. Название теста обещает то, чего нет.** Тест в `packages/core/tests/a8-agents.test.ts` называется «a revoked agent stays revoked for a delegation made after», а тело проверяет только отзыв делегирования. На деле после отзыва `scope: agent` новое делегирование тому же агенту живёт. В модели штампов так и должно быть: отзыв гасит прошлые токены, но не запрещает будущие. Неверно название; для «забанить агента» нужен отдельный механизм.

**P4. Отказ политики не отменяет побочных эффектов входа.** К моменту отказа субъект уже создан, вытеснение сделано, сессии других заявителей отозваны (в тесте «every step of every factor is audited» порядок `identity.mutate → policy.evaluate`). Если так задумано, это нужно описать: сейчас забаненный политикой человек продолжает вытеснять других.

## 3. Узкие места

- **Каждая проверка сессии — запрос к хранилищу эпох (Redis)**, в режиме сервиса ещё и HTTP. Цена мгновенного отзыва. Кэша нет; при недоступности Redis не проходит ни одна сессия. Закрыто при сбое — правильно, но не описано.
- **Записи отзыва копятся.** Каждый выход — запись на максимальный срок токена. На Redis при `maxmemory` отзыв перестаёт записываться (тест `redis-full`); адаптер памяти при переполнении отзывает всех (`memory-epoch-store`). Лимита на выход нет: циклом «вход–выход» зарегистрированный пользователь разлогинит всех (память) или сломает выход (Redis).
- **Аудит синхронно стоит в горячем пути отказов.** Каждый неверный токен, `rate-limited` и `invalid-proof` — запись. Мусорные токены превращаются в поток записей. Упавший аудит роняет `sessions.verify` исключением. На один вход — пять последовательных записей.
- **Лимит по цели — рычаг блокировки.** Любой может исчерпать лимит писем или попыток TOTP жертвы. К тому же отказ по второму scope уже потратил бюджет первого.
- **Уровни `device` и `agent` общие на весь тенант.** Отзыв `device: "laptop"` убивает и сессии другого человека, отзыв `agent: "mcp-client-7"` — агентов всех людей. HTTP защищён случайными `device`, но ядро и сервис принимают любые строки; пустой `id` при отзыве тоже проходит.
- **Outbox:** фиксированная задержка повтора без экспоненты и джиттера, у обработчика нет таймаута; обработчик дольше аренды даст параллельную двойную доставку.

## 4. Пробелы в покрытии сценариев

### Идентичности

- Обновление claims при повторном входе (P1, P2).
- Нет списка доверенных провайдеров для связывания по почте: любой фактор с `emailVerified: true` получает чужой аккаунт (класс атак nOAuth).
- Фактор может назваться любым `provider`: пространство имён не привязано к `factor.id`.
- Нет `issuer`: `sub` уникален только в пределах издателя.
- Нет сценария «легальный пользователь не подтвердил почту, и его вытеснили». Данные остаются (`evicted_at`), но пути слияния нет.
- Нет операции отвязки идентичности.

### Сессии и агенты

- Нет продления сессии, sliding-сессий и refresh-токенов.
- Нет списка активных сессий и делегирований: учёт целиком на приложении.
- У токена агента нет audience и привязки к отправителю (DPoP), которые ожидаются для MCP и OAuth 2.1.
- Нет сценария с тремя факторами подряд, хотя карта обещает «ещё один (другой) фактор».

### Email-link

- Ссылка не привязана ни к тенанту (`challenge(email)` без tenant), ни к браузеру, который её запросил. Пересланная ссылка работает на любом устройстве; ссылку на свой аккаунт можно подсунуть жертве (login CSRF).
- Нет теста и рекомендации на случай почтовых сканеров, которые открывают ссылку и сжигают одноразовый токен. Лечится страницей с POST-подтверждением.

### TOTP

- Хранилище есть только в памяти: нет адаптера для Redis или Postgres и нет контракта в `store-contracts`. На нескольких экземплярах фактор не работает.
- `remove` и `renewBackupCodes` не требуют свежего входа: угнанная сессия снимает второй фактор.

### Конфигурация и наблюдаемость

- `sessionMaximumAgeSeconds` у cookie и срок токена в ядре — две независимые настройки; расхождение не проверяется.
- Одноразовые токены и продолжения считают срок по локальным часам, сессии — по часам хранилища; на нескольких экземплярах это расходится.
- В записях аудита нет времени, идентификатора корреляции одного входа, IP и User-Agent.

### Интеграционные тесты

- 39 тестов Postgres и Redis пропускаются без переменных окружения, а CI в репозитории нет.

## 5. Расхождения с документацией

- `CONTRIBUTING.md`: «everything here is something the CI will check», но каталога `.github` нет.
- `README.md` и `README.ru.md` — одна строка. Нет установки, модели угроз, гарантий («закрыто при сбое», «минимум один раз», отзыв не запрещает будущие токены) и ограничений адаптера памяти.
- `examples/flow-map/README.md`: «19 путей», сборка выдаёт 23.
- Тест A25 называется «an unknown option is a compile error, not silence», а проверяет, что во время выполнения лишняя опция молча принимается. Для JS опечатка в `stepUpTimeToLiveMilliseconds` тихо отключает step-up (это отказ, а не открытый доступ).
- Название теста A8 — см. P3.
- Карта про outbox: «событие записывается вместе с изменением». Верно только при общем транзакционном исполнителе Postgres; для памяти и Redis и для операций самого ядра — нет, ядро событий не пишет.
- Узел `delete` на карте: «удаляет все идентичности». После коммита с таблицей субъектов удаляется субъект целиком, каскадом. Текст не обновлён.

## 6. Что сделано хорошо

Модель «закрыто при любом сбое» проведена последовательно и проверена property-тестами: отзыв, политика, подделки, сервис. Формы данных закрытые, без прототипов, с копированием и заморозкой. Тесты на гонки есть почти для каждого атомарного порта.

## 7. Адаптер памяти и Redis

Вопрос: не проще ли вместо адаптера, который хранит всё в памяти, взять клиент Redis (ioredis)?

**Адаптер памяти не замена Redis, а тестовый двойник.** Он нужен, чтобы ядро, примеры и контрактные тесты работали без внешних сервисов. Убирать его не стоит: тогда каждый тест потребует запущенный Redis. В продакшене его использовать нельзя: на нескольких экземплярах отзыв не общий, а перезапуск разлогинивает всех.

**Redis уже есть, и он не привязан к клиенту.** `@vow-auth/adapter-redis` принимает `RedisScriptRunner` — функцию `(script, keys, args) => Promise<unknown>`; в документации к ней есть примеры для ioredis, node-redis и Upstash. Зависимости от конкретного клиента нет, и вводить её не нужно: приложение передаёт свой клиент. Если выбирать клиент, стоит проверить текущий статус ioredis: насколько помню, сами авторы для новых проектов советуют node-redis.

**Что покрыто сейчас:**

| Порт | Память | Redis | Postgres |
|---|---|---|---|
| EpochStore (отзыв) | да | да | нет |
| MeterStore (лимиты) | да | да | нет |
| TokenStore (одноразовые токены) | да | нет | да |
| IdentityStore | да | нет | да |
| OutboxStore | да | нет | да |
| TotpStore | да | нет | нет |

**Чего не хватает и где это место:**

- **TotpStore в Redis — нужен в первую очередь.** Сейчас без него TOTP не работает на нескольких экземплярах. Атомарные `advance` и `spendBackupCode` естественно ложатся на Lua-скрипт, как в уже существующих хранилищах.
- **TokenStore в Redis — по желанию.** TTL и атомарное `GETDEL` подходят идеально; это позволит держать всё горячее в одном Redis. Postgres-версия уже есть.
- **IdentityStore в Redis — не нужен.** Идентичности — реляционные данные: на `vow_auth_subjects` приложение ставит внешние ключи, а вытеснение и поиск владельца почты — это запросы по нескольким полям. Им место в базе приложения.
- **OutboxStore в Redis — не нужен.** Смысл outbox — записать событие в той же транзакции, что и изменение данных приложения. Это возможно только в той же базе, то есть в Postgres.

Итог: адаптер памяти оставить для тестов и разработки, в Redis добавить `TotpStore` (и при желании `TokenStore`), идентичности и outbox оставить в Postgres.
