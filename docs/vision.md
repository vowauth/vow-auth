# Видение vow-auth

Статус: черновик для обсуждения, 2026-10-25.

Цель — движок входа и доступа, в котором люди и агенты получают доступ по одной модели. Каждое выданное право прослеживается до человека и отзывается целиком. Ни один плагин не может выдать доступ в обход движка.

## 1. Инварианты

Это не пожелания, а свойства, на каждое из которых должен быть тест.

1. **Один выпускающий.** Аккаунт-сессии, разрешения и токены создаёт только движок. Плагины приносят доказательства (кто это) и решения (можно ли), но не доступ.
2. **Один источник правды.** Жив ли доступ, решает дерево разрешений в базе. Кэш, короткий срок токена и штампы мгновенного отзыва могут только запретить раньше — разрешить вопреки базе они не могут.
3. **Одна модель для людей и агентов.** Сессия человека, вход в тенант, доступ агента, доступ субагента — всё это разрешения (grant) в одном дереве.
4. **Только сужение.** Дочернее разрешение не шире родительского: тот же тенант, `scope` и `audience` — подмножество, срок — не дольше.
5. **Изоляция тенантов на уровне протокола.** У каждого тенанта свой издатель (`iss`). Токен тенанта A не проходит стандартную проверку у тенанта B без нашего кода.
6. **Наружу — только стандарты.** Всё, что видят клиенты и ресурсные серверы, — OAuth 2.1, OIDC и авторизация MCP. Своё — только внутри движка.
7. **Безопасность по умолчанию — как у лидеров, строже — опцией.** Решения о доступе закрываются при сбое; вспомогательное (аудит, метрики) сбой не блокирует.
8. **Происхождение каждого действия.** Токен и запись аудита несут цепочку «человек → агент → субагент». На вопрос «кто это сделал» есть полный ответ.

## 2. Модель

```
Аккаунт (человек)
├── Идентичности: google|sub, email, passkey…         (принадлежат аккаунту)
├── Аккаунт-сессия на устройстве                       (grant, клиент — само приложение)
│   ├── Вход в тенант acme                             (grant, дочерний)
│   │   └── Агент, привязанный к этой сессии           (grant, опционально)
│   └── Вход в тенант globex                           (grant, дочерний)
└── Членства
    ├── acme   → субъект acme/7f3…                     (vow_auth_subjects)
    │   └── Агент «claude-desktop», scope: tasks:read  (grant, переживает выход)
    │       └── Субагент «search», scope: tasks:read   (grant через обмен токена)
    └── globex → субъект globex/a91…
```

| Сущность | Что это | Где |
|---|---|---|
| **Аккаунт** | Человек целиком, один на все тенанты | `vow_auth_accounts` |
| **Идентичность** | Способ доказать, что это он: провайдер + внешний id, почта | `vow_auth_identities`, у аккаунта |
| **Тенант** | Организация-клиент приложения со своими правилами входа | `vow_auth_tenants` |
| **Членство (субъект)** | Аккаунт внутри тенанта; свой id на тенант, на него приложение ставит внешние ключи | `vow_auth_subjects` (уже есть, получает `account_id`) |
| **Клиент** | Кто получает токены: само приложение, агент, чужое приложение; регистрация по стандарту | `vow_auth_clients` |
| **Разрешение (grant)** | «Этот человек в этом тенанте разрешил этому клиенту вот это»; узел дерева | `vow_auth_grants` |
| **Refresh-токен** | История ротации токенов разрешения | `vow_auth_refresh_tokens` |
| **Устройство** | Handle, выданный движком; к нему привязаны сессии | в разрешении |

Каждая запись разрешения запечатана движком (HMAC от её полей на внутреннем ключе). Запись, вставленная в базу в обход движка, токена не даёт.

## 3. Токены

| Токен | Кто получает | Формат | Срок по умолчанию | Проверка отзыва |
|---|---|---|---|---|
| Refresh аккаунт-сессии | только первое лицо (браузер, мобильное приложение) | случайный, в базе только хэш | 7 дней простоя со скольжением | при каждом обновлении, по базе |
| Токен доступа тенанта для человека | приложение | JWT (RFC 9068), `iss` тенанта | 5 минут | локально; мгновенно — опцией или для чувствительных операций |
| Refresh агента | клиент-агент | случайный, ротация, обнаружение повтора | по политике клиента | при каждом обновлении |
| Токен доступа агента | агент → ресурсный сервер | JWT, `aud` конкретного сервера (RFC 8707), `act` | 60 секунд | на своих серверах — всегда мгновенно; на чужих — introspection (RFC 7662) по желанию |

Поля токена доступа: `iss` (издатель тенанта), `sub` (id субъекта в тенанте), `aud`, `exp`, `iat`, `jti`, `client_id`, `scope`, `sid` (id разрешения), `auth_time`, `amr`, `acr`. У агентов дополнительно `act` (цепочка исполнителей, RFC 8693) и при DPoP — `cnf`.

Подпись — через `jose` (точная версия, типы наружу не выходят): ES256 по умолчанию, RS256 и EdDSA опцией. Ключи задаются списком: первый подписывает, все публикуются в JWKS издателя.

## 4. Потоки

### 4.1. Вход человека

Фактор приносит доказательство → движок находит или создаёт аккаунт → политика регистрации (если аккаунт новый) → политика входа → аккаунт-сессия на устройстве.

Вытеснение неподтверждённых претензий на почту выполняется только после разрешения входа. Связывание по почте — только для доверенных провайдеров (`trustedProviders`), данные провайдера обновляются при каждом входе.

### 4.2. Вход в тенант и переключение

Из аккаунт-сессии движок выдаёт разрешение тенанта без повторного ввода, если аккаунт — член тенанта и выполнены правила тенанта:

- разрешённые провайдеры (например, «только SSO компании»);
- обязательные факторы (например, «TOTP обязателен»);
- свежесть входа.

Если правило не выполнено — step-up именно для этого тенанта. Переключение тенанта — это выдача ещё одного дочернего разрешения, а не новый вход. В соседних вкладках разные тенанты не мешают друг другу.

### 4.3. Step-up

Внутри — как сейчас: политика просит фактор, второй шаг по одноразовому продолжению, несколько попыток в пределах лимита. Для ресурсных серверов — стандартно: `acr`/`amr`/`auth_time` в токене и ответ «нужен вход посвежее» по RFC 9470.

### 4.4. Подключение агента (MCP)

1. Агент обращается к ресурсному серверу, получает 401 с `WWW-Authenticate` и адресом метаданных ресурса (RFC 9728).
2. Находит сервер авторизации по метаданным (RFC 8414).
3. Регистрируется: Client ID Metadata Document или динамическая регистрация (RFC 7591).
4. Открывает `/authorize` с PKCE и `resource` (RFC 8707).
5. Человек входит (или уже вошёл), выбирает тенант, видит запрошенные права и соглашается. Страницу рисует приложение, движок даёт данные и принимает решение.
6. Агент меняет код на токены в `/token`.

Разрешение агента по умолчанию — дочернее к членству: оно переживает выход человека, как обычное согласие OAuth. Опция «привязать к сессии» делает его дочерним к разрешению тенанта на этом устройстве.

### 4.5. Агент вызывает субагента или другой сервер

Обмен токена (RFC 8693): агент предъявляет свой токен и токен исполнителя (`actor_token`). Движок выдаёт дочернее разрешение:

- только сужение (инвариант 4);
- цепочка `act` дополняется новым исполнителем;
- ограничение глубины (по умолчанию 3);
- каждый исполнитель аутентифицируется сам — вставить себя в чужую цепочку нельзя (защита от «delegation chain splicing»).

### 4.6. Подтверждение человеком (позже)

Для опасных действий — асинхронное подтверждение: запрос в состоянии «ждёт человека», человек подтверждает на своём устройстве, агент получает короткий токен ровно на это действие (`authorization_details`, RFC 9396). Это подход CIBA, его же использует Auth0.

### 4.7. Отзыв

Одна операция движка по любому уровню: тенант, аккаунт, членство, устройство, клиент, разрешение. Отзывается всё поддерево:

- в базе — сразу и навсегда;
- обновление токенов отказывает сразу;
- токены доступа на своих серверах умирают мгновенно через штампы (они живут не дольше токена доступа и могут только запретить);
- на чужих серверах — при истечении (60 секунд для агентов) или через introspection.

Выход с устройства отзывает аккаунт-сессию с поддеревом. Агенты с самостоятельным согласием живут, пока человек их не отключит («отключить все агенты» — отдельное действие).

## 5. Плагины: что можно и чего нельзя

| Вид | Получает | Отдаёт |
|---|---|---|
| Фактор (почта, TOTP, passkey, внешний OIDC) | ответ человека, контекст (тенант, субъект и прошлые доказательства на втором шаге) | claims → движок чеканит доказательство |
| Политика (регистрация, вход, тенант, клиент) | данные решения | решение |
| Страница согласия (приложение) | данные запроса, одноразовый билет | решение человека по билету |
| Наблюдатель | события только для чтения | ничего |

Никакой плагин не получает ключи подписи, хранилище разрешений или функцию выпуска. Это проверяется тестом поверхности API и тестом «разрешение, вставленное в базу напрямую, не даёт токена». Именно этим мы закрываем проблему Better Auth, где плагин может создать сессию сам.

## 6. Мультитенантность

- **Издатель на тенанта:** `https://auth.example.com/t/{tenant}`, метаданные и JWKS у каждого.
- **Ключи подписи:** общие по умолчанию, свои на тенанта — опцией для B2B, которому нужна изоляция.
- **`sub` в тенанте — id субъекта (членства), а не аккаунта.** Тенант B не может по `sub` сопоставить человека с тенантом A. Id аккаунта видит только само приложение.
- **Правила тенанта** (провайдеры, факторы, свежесть, допустимые клиенты-агенты) проверяются при выдаче разрешения тенанта.
- **Администратор тенанта** отзывает членство, видит и отключает агентов в своём тенанте, не видит других тенантов человека.
- **Cookie:** один refresh аккаунт-сессии на домене входа, токены доступа тенантов — по запросу, имя cookie с тенантом. Соседние вкладки с разными тенантами не конфликтуют.

## 7. Чем это лучше лидеров

По открытым данным на 2026-10-25; где не уверен, сказано прямо.

| Возможность | Better Auth | Auth0 | Clerk | vow-auth |
|---|---|---|---|---|
| Плагин не может выдать сессию сам | нет: плагин создаёт сессию через внутренний адаптер | закрытый SaaS, плагинов в этом смысле нет | закрытый SaaS | **да, инвариант 1 с тестами** |
| Аккаунт + организации | плагин `organization`: активная организация в сессии | Organizations | активная организация в токене (`org_id`) | **разрешение на тенант, переключение без нового входа, вкладки не мешают** |
| Издатель на тенанта | нет | тенант Auth0 = издатель; организации внутри одного издателя | один издатель | **да** |
| Агенты по MCP/OAuth 2.1 | есть плагины (возможности не проверял) | да (Auth0 for AI Agents) | не проверял | **да, той же моделью, что и люди** |
| Цепочки субагентов с сужением | нет | обмен токена есть, сужение по цепочке не проверял | нет | **да: дерево, только сужение, глубина, защита от вставки** |
| Мгновенный отзыв агента | задержка до `cookieCache` | короткий срок токена | до 60 секунд | **мгновенно на своих серверах** |
| Подтверждение человеком | нет | да (CIBA, Guardian) | нет | позже, тем же стандартом |
| Происхождение действия в аудите | нет | тема поднята в их статье «closing the audit gap», возможности не проверял | нет | **цепочка `act` в каждом токене и записи** |
| Открытый код, своя база | да | нет | нет | да |

Чего у лидеров нет ни у кого сразу: одна модель для людей и агентов с деревом, сужением, мгновенным отзывом и запретом на выпуск в обход — в открытом движке на своей базе.

## 8. Чего мы не делаем

- Авторизация действий в приложении (FGA, роли, права на объекты): наш предел — `scope`, что он значит, решает приложение.
- Хранилище чужих токенов (Token Vault у Auth0).
- Доставка писем, очереди, outbox.
- CAPTCHA и обнаружение ботов.
- Лимиты как сервис для приложения (свои маршруты входа ограничиваем сами).
- Интерфейс управления пользователями.
- SAML и SCIM — не сейчас; модель членства не должна им мешать.

## 9. Хранилища

- **Postgres:** аккаунты, идентичности, тенанты, субъекты, клиенты, разрешения, refresh-токены. Схема и префикс настраиваются, миграции версионированы.
- **Redis (необязательно):** штампы мгновенного отзыва, лимиты маршрутов входа.
- **Память:** тесты и разработка.

## 10. Риски и цена

- **Сложность.** Модель шире текущей; держим её за счёт инвариантов и контрактных тестов.
- **Черновики спецификаций.** Предложения по агентам (обмен токена для агентов, профили исполнителей) — индивидуальные черновики IETF, не стандарты. Строимся на RFC 8693, поля из черновиков держим за флагами.
- **Размер токена.** Цепочка `act` растёт с глубиной; ограничение глубины держит токен в пределах cookie и заголовка.
- **Топология доменов.** Домен входа отдельно или на домене приложения — влияет на cookie; решить до HTTP-слоя.

## 11. Этапы

0. **Удалить чужие зоны:** outbox, защита исходящих запросов, публичный счётчик, `authorize`, `service`, `doctor`, `flow-map`, статистика Redis, публичная печать.
1. **Аккаунты:** идентичности у аккаунта, членства (субъекты), `trustedProviders`, обновление claims при входе, политика регистрации, вытеснение после разрешения.
2. **Разрешения:** дерево, refresh с ротацией и обнаружением повтора, печать записей, JWT через `jose`, JWKS, издатель на тенанта.
3. **Вход по новой модели:** аккаунт-сессия, разрешения тенанта, правила и step-up тенанта, устройство от движка; удалить старые сессии и агентов.
4. **HTTP:** cookie и Bearer, `/token`. Здесь же собрать новый небольшой пример приложения вместо удалённого `examples/playground` — как только первый поток (вход → разрешение тенанта → проверка токена) заработает целиком.
5. **Сервер авторизации для агентов:** клиенты (CIMD, RFC 7591), `/authorize` с PKCE и согласием, RFC 8414, 9728, 8707, 7009, 7662, 9470.
6. **Цепочки агентов:** обмен токена RFC 8693 с сужением и `act`, мгновенный отзыв на своих серверах.
7. **Позже:** подтверждение человеком (CIBA + RFC 9396), DPoP (RFC 9449).

## 12. Открытые вопросы

Подробный разбор с вариантами, примерами и рынками СНГ и АСЕАН — в `docs/vision-analysis.md`. Там же новый главный вопрос 0: где живёт аккаунт при требованиях локализации данных.

1. **Id в тенанте:** `sub` — id субъекта, id аккаунта только приложению. Согласны?
2. **Чей аккаунт:** только личные аккаунты или тенант может управлять аккаунтами своих сотрудников (домен компании, корпоративный SSO, как GitHub EMU)? Предлагаю: сейчас личные, в членстве оставить место под управляемые.
3. **Разрешение агента по умолчанию:** дочернее к членству (переживает выход, как OAuth) или к сессии? Предлагаю: к членству.
4. **Глубина цепочки агентов по умолчанию:** 3?
5. **Домен входа:** отдельный (`auth.app.com`) или на домене приложения?
6. **Тенанты и членства:** создание тенанта и приглашения — часть движка (API без интерфейса) или приложения? Предлагаю: движок хранит членство и даёт API приглашения одноразовым токеном, всё остальное — приложение.
