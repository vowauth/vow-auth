# Видение: разбор вопросов, будущие боли, рынки СНГ и АСЕАН

Статус: черновик к `docs/vision.md`, 2026-10-25. Факты о законах взяты из обзоров юридических фирм и новостей, а не из официальных текстов. Перед решениями, которые от них зависят, нужна проверка юристом.

## Часть 1. Рынки, на которые идём первыми

### 1.1. Что требуют законы

| Страна | Требование | Что это значит для движка |
|---|---|---|
| **Россия, 152-ФЗ** | С 1 июля 2025 запись и извлечение персональных данных граждан РФ в базах за рубежом запрещены (23-ФЗ); обязанность распространена и на обработчиков по поручению. Штрафы за нарушение локализации — до 18 млн ₽ при повторном. | Аккаунты граждан РФ хранятся в РФ. «Один глобальный аккаунт в одной базе» для смешанной аудитории незаконен. |
| **Россия, 406-ФЗ** | Владельцы российских сайтов аутентифицируют пользователей только через: российский номер телефона, Госуслуги (ЕСИА), Единую биометрическую систему или российские системы аутентификации (VK ID, Яндекс ID, Сбер ID и подобные). Регистрация через иностранную почту и Google запрещена. Срок сдвигали на 1 января 2025; по сообщениям, в июне 2026 Дума одобрила штрафы (до 700 тыс. ₽ для юрлиц). Уже зарегистрированные пользователи сохраняют доступ. | **Наш единственный основной фактор, ссылка на почту, для регистрации в РФ не годится.** Нужен фактор телефона и коннекторы к ЕСИА и российским ID. Правило «какими способами можно войти» должно задаваться тенантом. |
| **Казахстан** | Хранение персональных данных на территории РК с 2015 года; применение спорно, но требование есть. | Локализация в РК. |
| **Узбекистан** | С 15 апреля 2021 данные граждан хранятся на серверах в Узбекистане, базы регистрируются в государственном реестре. | Локализация в УЗ плюс регистрация базы. |
| **Вьетнам, указ 147/2024** | С 25 декабря 2024 соцсети (и местные, и иностранные) подтверждают аккаунты вьетнамским номером телефона; без номера — личным идентификационным номером (VNeID). Без подтверждения нельзя публиковать и комментировать. | Тенанту с соцфункциями нужно: «подтверждён вьетнамский номер или VNeID». |
| **Вьетнам, закон о персональных данных (с 1 января 2026)** | Режим на согласии; трансграничная передача — с оценкой воздействия; повышенные требования к соцсетям, финансам, здравоохранению. Локализация для ряда компаний — по указу 53/2022 (не проверено в этом поиске). | Записи согласий, учёт передачи данных за рубеж. |
| **Индонезия, закон 27/2022** | Действует в полном объёме с 17 октября 2024. Уведомление об утечке в течение 3×24 часов. | Аудит событий входа должен позволять быстро понять масштаб утечки. |
| **Малайзия, поправки 2024** | Обязательный DPO, уведомление об утечке, переносимость данных (вступают в 2025). | Выгрузка данных аккаунта по запросу. |
| **Сингапур, Singpass** | Переход на FAPI 2.0 до 31 декабря 2026: PAR, DPoP, PKCE только S256, аутентификация клиента подписанным JWT, ID-токен всегда зашифрован (JWE). | Коннектор к Singpass должен уметь FAPI 2.0. Сервер авторизации по профилю FAPI 2.0 — сильный аргумент для финтеха АСЕАН. |

Не проверял: Таиланд (PDPA, ThaID), Филиппины (Data Privacy Act, PhilSys), Малайзия (MyDigital ID), Казахстан (eGov, ЭЦП), Узбекистан (OneID). Требования ЕСИА к подписи по ГОСТ (широко известно, что `client_secret` подписывается ГОСТ Р 34.10-2012 через КриптоПро) — в поиске подтверждено только сторонними проектами.

### 1.2. Что характерно для этих рынков, кроме законов

- **Телефон — основной идентификатор.** Почта вторична, у многих её нет или она не используется.
- **SMS дорогие и подвержены накрутке (SMS pumping, IRSF).** Оператор назначения получает часть оплаты за каждое сообщение и делится с атакующим. Telegram Gateway доставляет код за $0,01 и только при доставке в срок, но работает лишь для пользователей Telegram. Популярны также WhatsApp, Zalo (Вьетнам), LINE (Таиланд).
- **Перевыпуск номеров.** Операторы отдают номер новому абоненту через 70–180 дней (по оценкам поставщиков). Исследование 2021 года: около 66% выборки перевыпущенных номеров всё ещё были привязаны к аккаунтам прежних владельцев. Вход «только по SMS» на старый номер — захват аккаунта.
- **Общие устройства и слабые телефоны:** семейный смартфон, нестабильная связь, дешёвый Android.
- **Национальные системы ID как основной вход** для госсектора и финансов: ЕСИА, Singpass, VNeID, eGov, OneID.
- **B2B хочет местных корпоративных провайдеров:** Яндекс 360, VK WorkSpace, Битрикс24 — наряду с Microsoft и Google.

### 1.3. Вывод для видения

Рынок ломает одно из базовых допущений: **глобальный аккаунт в одной базе для смешанной аудитории невозможен.** Гражданин РФ, гражданин Узбекистана и клиент из Сингапура в одном приложении — это три разных места хранения. Решение — в части 3, вопрос 0.

## Часть 2. Боли, которых ещё не видно

Ниже то, что почти никто не учитывает сейчас, но что всплывёт в ближайшие 1–3 года. По каждой боли: что в движке должно быть сразу, чтобы не переделывать потом.

1. **Резиденция данных против глобального аккаунта.** Связь с гражданством, а не с тенантом. Человек переезжает, меняет номер, имеет два гражданства. *Сразу:* развёртывание = одна зона данных; аккаунт имеет домашнюю зону; связь между зонами — только стандартной федерацией с попарными (pairwise) id. Подробнее — вопрос 0.
2. **Законы о способах входа меняются, и старых пользователей приходится «доводить».** По 406-ФЗ уже зарегистрированные пользователи пока сохраняют доступ, но следующая поправка может потребовать привязать номер к сроку. *Сразу:* механизм «требование к аккаунту»: тенант или зона объявляет «к такой-то дате нужен подтверждённый российский номер», движок при входе требует его добавить (как step-up, но для идентичности). Ни у кого из лидеров этого нет как функции.
3. **Криптографическая гибкость.** ГОСТ для российского госсектора; профиль FAPI 2.0 для Singpass и финтеха; постквантовые подписи (ML-DSA) через несколько лет. `jose` не умеет ГОСТ. *Сразу:* подпись и проверка за нашим интерфейсом с алгоритмом на издателя; `jose` — одна из реализаций.
4. **Расползание агентов и «зомби»-доступы.** У человека будут десятки агентов, большинство заброшено, но доступ жив. *Сразу:* время последнего использования разрешения; автоматическое истечение неиспользуемых (по умолчанию, например, 30 дней); список «кто имеет доступ» с отключением одним действием для человека и для администратора тенанта.
5. **Действительный токен, вредное действие.** Prompt injection заставляет агента с законным доступом сделать вредное. Короткий срок токена тут не помогает. *Сразу:* минимальные права по умолчанию; поле для `authorization_details` (RFC 9396) в разрешении; подтверждение человеком как состояние разрешения (CIBA) — заложить в модель, реализовать позже.
6. **Агенты регистрируют аккаунты сами.** «Зарегистрируй меня в сервисе X» — массовые регистрации от имени людей; CAPTCHA против ИИ не работает. *Сразу:* в аккаунте и разрешении — признак «создано агентом от имени человека» и цепочка происхождения; политика регистрации видит, что это агент.
7. **Перехват кодов в реальном времени.** Голосовые и чат-боты убеждают человека продиктовать код из SMS или переслать ссылку. Это массово в СНГ уже сейчас. *Сразу:* коды привязаны к устройству, запросившему вход (код с другого устройства не принимается без подтверждения); приоритет устойчивых к фишингу факторов (passkeys); предупреждение в тексте сообщения.
8. **Восстановление доступа становится главной целью атак.** Чем меньше паролей, тем больше атак на «потерял телефон»: SIM-swap, перевыпуск номера, социальная инженерия поддержки с подделкой голоса. *Сразу:* восстановление как отдельный поток с задержкой, уведомлением на все прежние каналы и запретом немедленно отключать старые факторы.
9. **Не только MCP.** Протокол A2A (Google) описывает схемы безопасности в карточке агента: OAuth 2.0, OpenID Connect, ключи API, mTLS. *Сразу:* сервер авторизации — обычный OAuth 2.1, без привязки к MCP; метаданные пригодны для любого протокола.
10. **Кто разрешил это действие — вопрос для суда и регулятора.** *Сразу:* журнал согласий (кто, кому, что, когда, по какой версии текста) и защищённый от правки аудит (цепочка хэшей). Это же нужно для уведомлений об утечке (72 часа в Индонезии) и для режимов на согласии (Вьетнам, 152-ФЗ).
11. **Стоимость каналов кода.** SMS дорожают, а накрутка съедает бюджет. *Сразу:* доставка кода — плагин канала (SMS, Telegram, WhatsApp, Zalo, LINE) с маршрутизацией по стране и откатом на запасной; лимиты по стране и префиксу номера.

## Часть 3. Открытые вопросы — подробно

### Вопрос 0 (новый, главный). Где живёт аккаунт

Из части 1: данные граждан РФ, Казахстана и Узбекистана нужно хранить в стране. Глобальный аккаунт в одной базе для смешанной аудитории невозможен.

| Вариант | Как | За | Против |
|---|---|---|---|
| **А. Одна зона на развёртывание, аккаунт локален** | Каждое развёртывание (RU, KZ, UZ, SG…) — отдельная зона со своей базой и издателями. Аккаунт существует только в своей зоне. | Просто; локализация соблюдается по построению; ничего не утекает. | Человек с аккаунтами в двух зонах — два разных человека; нет «единого входа» между зонами. |
| **Б. Зоны + федерация** | Как А, плюс зона может доверять другой как внешнему OIDC-провайдеру. Аккаунт из SG входит в тенант RU, и в RU хранится только попарный id и минимум данных. | Локализация соблюдается; есть сквозной вход, где он нужен и разрешён. | Перенос данных между зонами — юридический вопрос (трансграничная передача); сложнее. |
| **В. Глобальный аккаунт** | Одна база на всех. | Проще всего для продукта. | Незаконно для смешанной аудитории в СНГ. |

**Рекомендация: А сейчас, Б позже.** Движок не знает о «зонах» как сущности: зона — это одно развёртывание. Чтобы Б стал возможен без переделки, сразу нужны две вещи: попарный `sub` (вопрос 1) и фактор «внешний OIDC-провайдер», которым может быть и другая наша зона.

### Вопрос 1. Что агенты и сервисы видят в `sub`

| Вариант | Примеры | За | Против |
|---|---|---|---|
| **А. Id субъекта в тенанте (попарный)** | Slack: свой id пользователя в каждом workspace; Apple Sign In: попарный `sub` на команду разработчика; OIDC pairwise identifiers | Тенанты не могут сопоставить человека; федерация между зонами (вопрос 0); удаление тенанта чистое; внешний ключ приложения совпадает с `sub` | Функции, сквозные для тенантов (общий профиль, уведомления из всех workspace), требуют id аккаунта отдельно |
| **Б. Id аккаунта** | Auth0 Organizations: один `user_id` во всех организациях + `org_id`; Clerk: один id пользователя + `org_id` | Проще для приложения; одна сущность везде | Сторонний агент или ресурсный сервер видит, что это тот же человек в другом тенанте; ломает вариант Б из вопроса 0 |
| **В. А в токенах, id аккаунта только первому лицу** | Комбинация | Изоляция наружу и удобство внутри | Два id в модели; приложение должно понимать, какой где |

**Рекомендация: В.** Сторонние клиенты и чужие ресурсные серверы видят только попарный id. Само приложение (первое лицо) получает и id аккаунта, через отдельное поле, недоступное сторонним клиентам.

### Вопрос 2. Чей аккаунт: личный или управляемый тенантом

| Вариант | Примеры | За | Против |
|---|---|---|---|
| **А. Только личные** | Notion, Figma на базовых тарифах | Просто; человек владеет аккаунтом; нет вопросов, кто оператор данных | Компания не может управлять уходом сотрудника, кроме как отозвать членство; подрядчики и сотрудники смешаны |
| **Б. Только управляемые** | Microsoft рабочие аккаунты (Entra), Google Workspace | Полный контроль компании | Неудобно для B2C и смешанных сценариев |
| **В. Оба, с захватом домена** | GitHub: личные и Enterprise Managed Users; Google: личные и Workspace; Figma и Notion: подтверждённый домен делает аккаунты с корпоративной почтой управляемыми | Покрывает B2B и B2C | Захват существующих личных аккаунтов по домену — вопрос согласия и приватности; кто оператор персональных данных (по 152-ФЗ) меняется |

Для СНГ и АСЕАН: B2B требует контроля ухода сотрудника, особенно банки и госкомпании. Но корпоративный вход там часто через свой провайдер (Яндекс 360, VK WorkSpace, Entra), и «управляемость» идёт через SSO, а не через наш аккаунт.

**Рекомендация:** сейчас А, но в модели сразу поле «владелец: сам или тенант» и правило тенанта «вход только через наш SSO». Захват домена — вместе с SSO и SCIM, позже.

### Вопрос 3. Разрешение агента по умолчанию: к членству или к сессии

| Вариант | Примеры | За | Против |
|---|---|---|---|
| **А. К членству (переживает выход)** | Коннекторы Claude.ai и ChatGPT, OAuth-приложения GitHub, сторонний доступ Google — живут, пока их не отключат в настройках | Агент работает, когда человек не в сети, а это и есть смысл агентов (фоновые задачи); привычно по OAuth | Забытые агенты с живым доступом (боль 4) |
| **Б. К сессии** | Расширения браузера, токены «пока открыта вкладка» | Ничего не живёт после выхода | Фоновые агенты невозможны; человек каждый раз подключает заново |

Ваше опасение «за 5 минут агент сделает больше вреда» относится к обоим вариантам. Защищают права и подтверждение опасных действий, а не привязка к сессии.

**Рекомендация: А по умолчанию,** плюс:
- истечение при неиспользовании (по умолчанию 30 дней) и повторное согласие раз в N дней — опцией тенанта;
- правило тенанта «агенты только с привязкой к сессии» — для банков и госсектора;
- опасные права — только с подтверждением человеком (когда появится CIBA).

### Вопрос 4. Глубина цепочки агентов по умолчанию

| Вариант | За | Против |
|---|---|---|
| **2** | Минимальная поверхность атаки | Типичная схема «ассистент → сервер инструментов → внешний API» уже упирается в предел |
| **3** | Покрывает «человек → ассистент → инструмент → API»; токен небольшой (каждый уровень `act` — около 100–200 байт) | Оркестраторы «планировщик → исполнители → инструменты» могут не влезть |
| **5 и больше** | Сложные многоагентные системы | Цепочку сложнее аудировать; больше места для вставки чужого звена |

Стандарта по умолчанию нет. Черновик AAP вводит счётчик глубины, но значение не задаёт.

**Рекомендация: 3 по умолчанию, тенант поднимает до 5.** Глубже — только новым согласием человека.

### Вопрос 5. Домен входа

| Вариант | Примеры | За | Против |
|---|---|---|---|
| **А. На домене приложения (`app.com/auth`)** | Better Auth | Проще всего; cookie первого лица | Издатель привязан к домену приложения; несколько приложений одним аккаунтом не поделятся |
| **Б. Поддомен того же сайта (`auth.app.com`)** | Clerk (Frontend API на поддомене, Account Portal на `accounts.`); Auth0 с собственным доменом | Cookie того же сайта: ограничения браузеров на сторонние cookie не мешают; стабильный адрес издателя (важно для клиентов OAuth и MCP); узнаваемый домен против фишинга | Нужен DNS и сертификат |
| **В. Отдельный домен (`app-id.com`)** | Google (`accounts.google.com`), Microsoft (`login.microsoftonline.com`) | Единый вход для многих продуктов | Сторонние cookie блокируются (Safari уже, Chrome частично): только переходы верхнего уровня, никаких iframe |

Особенность B2B в СНГ и АСЕАН — white-label: у тенантов свои домены (`login.acme.kz`). Это или отдельный издатель на домене тенанта, или переход на наш домен.

Зоны данных (вопрос 0) удобно разводить поддоменами: `auth.ru.app.com`, `auth.sg.app.com`.

**Рекомендация: Б по умолчанию, но движок ничего не зашивает:** адрес издателя задаётся на тенанта, включая собственные домены тенантов.

### Вопрос 6. Тенанты, приглашения, роли

| Вариант | Примеры | За | Против |
|---|---|---|---|
| **А. Только членство** | — | Минимум кода | Каждое приложение пишет приглашения само, и делает это небезопасно (приглашение — это выдача доступа) |
| **Б. Членство + приглашения + метки ролей в токене** | Auth0 Organizations (участники, приглашения, роли), Clerk Organizations (приглашения, `org_role`, права в токене), плагин `organization` у Better Auth (приглашения, роли owner, admin, member, команды) | Так делают все лидеры; приглашение — это вход в тенант, значит, наша зона | Метки ролей легко превратить в систему прав — надо держать границу |
| **В. Полная система ролей и прав** | Auth0 RBAC, Clerk permissions | Всё из коробки | Это авторизация действий — мы договорились туда не идти |

**Рекомендация: Б.** Движок отвечает за жизненный цикл членства:
- пригласить одноразовым токеном, принять, приостановить, удалить;
- метки ролей хранятся и попадают в токен.

Что значат метки и что можно делать, решает приложение. Создание тенанта — простой API движка, без интерфейса.

## Часть 4. Что меняется в видении

1. **Зона данных** — новый базовый принцип. Одно развёртывание = одна зона; попарный `sub` сразу; федерация зон — позже.
2. **Правила тенанта о способах входа** поднимаются с «удобства» до «обязательного требования рынка» (406-ФЗ, указ 147/2024).
3. **Новые факторы в приоритете:** телефон (SMS и мессенджеры как каналы-плагины, защита от накрутки) — раньше ссылки на почту по значимости для СНГ; внешний OIDC-провайдер (ЕСИА, VK ID, Яндекс ID, Сбер ID, Singpass, VNeID) — как один фактор с профилями.
4. **Требования к аккаунту** («к дате нужен подтверждённый номер») — новая функция, которой нет у лидеров.
5. **Криптографическая гибкость:** подпись за интерфейсом, алгоритм на издателя; `jose` — реализация по умолчанию.
6. **Агенты:** истечение неиспользуемых разрешений, учёт последнего использования, правило тенанта «только с привязкой к сессии».
7. **Журнал согласий и защищённый аудит** — часть базы, а не продуктовая надстройка: этого требуют законы о персональных данных.
8. **Восстановление доступа** — отдельный поток с задержкой и уведомлениями.
9. **Членство, приглашения и метки ролей** — в движке.
