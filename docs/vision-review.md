# Ревизия решений и скорректированный план

Статус: 2026-10-25. Повторная проверка всех принятых решений: что упустили, что взято из устаревших подходов, где есть путь проще и безопаснее. Решения, требующие согласования, помечены «на решение».

## 1. Найдено и исправлено при проверке

| Что | Почему опасно | Исправление | Коммит |
|---|---|---|---|
| Домен и цель печати и одноразовых токенов склеивались через `/` | Фактор `x` выпускал значение с целью `y/p`, которое фактор `x/y` принимал за своё с целью `p` | Домен и цель кодируются парой JSON; id фактора — простое имя `[a-z][a-z0-9-]*` | `7e2d134` |
| Секрет проверялся только по длине | `aaaa…`, `abab…`, `0123…`, `changeme-…` длиной 32 проходили; по одному токену такой секрет подбирается офлайн, после чего подделывается всё | Секрет должен выглядеть сгенерированным: ≥16 разных символов, без повтора короткой части, ≥128 бит по частоте собственных символов. `openssl rand -base64 32` и `-hex 32` проходят | `7e2d134` |
| Одно значение секрета под двумя версиями | Ротация, которая ничего не ротирует | Отказ при запуске | `7e2d134` |

**Осталось по секретам:** одинаковый секрет в двух развёртываниях (например, staging и prod, или две зоны данных) — значения, запечатанные в одном, открываются в другом. Обнаружить это изнутри одного развёртывания нельзя. Закрываем на этапе 2: адрес издателя входит в вывод ключей и в токен, и значение чужого издателя не открывается даже при том же секрете. До этого — разные секреты на каждое окружение.

## 2. Что стоит изменить

### 2.1. Сессия в браузере: непрозрачный токен вместо JWT и refresh — принято

**Было решено (F):** короткий JWT доступа и refresh-токен с ротацией для всех, включая браузер.

**Что не так.** Для браузера этот подход сложнее и не безопаснее:

- **Стандарт.** Новый BCP IETF по браузерным приложениям (RFC 10017 / draft-ietf-oauth-browser-based-apps; статус публикации в найденных источниках расходится) прямо советует не показывать токены JavaScript вообще. Рекомендуемый вариант — backend-for-frontend: в браузере только HttpOnly-cookie сессии, токены на сервере. Мы и есть этот сервер.
- **Гонки.** Ротация refresh-токена в нескольких вкладках — известный источник ложных «краж» и разлогинивания (окно на гонки, повторная выдача, синхронизация между вкладками).
- **Отзыв.** JWT в cookie живёт до истечения; непрозрачная сессия отзывается сразу.

**Предлагаю.** Две формы одного разрешения:

| Клиент | Что держит | Как проверяется |
|---|---|---|
| Браузер (своё приложение) | Непрозрачный токен сессии в HttpOnly-cookie `__Host-`; в базе — только его хэш в записи разрешения | Поиск разрешения по хэшу; при желании короткий кэш (как `cookieCache` у Better Auth). Скользящий срок. Новый токен после входа и после step-up (защита от фиксации сессии) |
| Мобильное приложение, API, агенты (клиенты OAuth) | JWT доступа (`jose`) + refresh с ротацией и обнаружением повтора | Подпись локально; мгновенно — по записи разрешения |

Источник правды один: запись разрешения. Отличается только то, что получает клиент. Так устроен Better Auth (токен сессии в базе плюс необязательный кэш), и это совместимо с привязкой cookie к устройству (DBSC) в будущем.

**Стандарт.** Отдельного RFC «непрозрачная сессия» нет: OAuth и OIDC описывают, как сервер выдаёт доступ другим, а сессия своего приложения — внутреннее дело сервера. Требования к ней задают четыре документа. Проверять реализацию удобнее всего по OWASP ASVS — это проверяемый стандарт с номерами требований, по нему проходят аудиты.

| Документ | Что требует | Как у нас |
|---|---|---|
| RFC 10017 (BCP 212), OAuth 2.0 for Browser-Based Applications | Из трёх схем только BFF вообще не пускает токены в JavaScript: сервер — конфиденциальный клиент, браузеру — только HttpOnly-cookie сессии | Мы и есть этот сервер. Своему браузерному приложению OAuth не нужен совсем: cookie и есть сессия |
| NIST SP 800-63B-4, «Session management» | Сессия держится на владении секретом, выданным хостом сессии при входе (SHALL); секрет — из одобренного генератора случайных чисел, не короче 64 бит; при выходе стирается или аннулируется; cookie не заменяет аутентификацию; на AAL2 повторный вход не реже раза в 24 часа и после часа бездействия (SHOULD) | Токен 256 бит из `crypto.getRandomValues`; скользящий срок и абсолютный предел; выход — пометка записи |
| OWASP ASVS 4.0.3, V3 | 3.2.1 — новый токен при входе; 3.2.2 — не меньше 64 бит; 3.3.1 — выход и истечение аннулируют токен; 3.3.2 — периодический повторный вход; 3.4.1–3.4.4 — `Secure`, `HttpOnly`, `SameSite`, префикс `__Host-`; 3.5.1 — пользователь может отозвать доступ связанных приложений | Новый токен после входа и step-up; список и отзыв разрешений, включая агентов |
| RFC 6265bis (cookie), префикс `__Host-` | Браузер принимает такую cookie только с `Secure`, `Path=/` и без `Domain`: она привязана к точному хосту, поддомен её не перезапишет | Имя cookie с префиксом `__Host-` |

JWT в cookie нарушает ASVS 3.3.1 без серверного состояния: выход не аннулирует уже выданный токен. Хранить в базе только хэш токена — практика Lucia и Cloudflare `workers-oauth-provider`, не требование стандарта: украденные из базы хэши не дают войти.

### 2.2. Убрать штампы отзыва — принято

**Было:** хранилище эпох, цепочки «тенант → пользователь → устройство → сессия» со штампами, срок ключей = максимальный срок токена.

**Что не так.** Это наш собственный механизм, и с появлением записей разрешений он стал вторым источником правды. Он требует отдельного порта, математики сроков ключей и особого поведения памяти при переполнении («отозвать всех»). Мгновенную проверку даёт и поиск записи разрешения:

- браузер — поиск по хэшу токена (п. 2.1);
- JWT на своих серверах — поиск по `sid` с кэшем на несколько секунд (по сути, introspection, RFC 7662);
- чужие серверы — короткий срок токена или introspection.

**Предлагаю:** удалить `EpochStore`, цепочки и штампы; Redis остаётся необязательным кэшем записей разрешений и хранилищем лимитов. Отзыв уровня (тенант, аккаунт, членство, устройство, клиент) — это обновление записей в базе одной операцией. Долгоживущего процесса не нужно: кэш ленивый, по сроку.

**Пример: как сейчас.** Алиса вошла с телефона. В cookie лежит запечатанная цепочка «тенант acme → Алиса → телефон → сессия s1». У каждого звена — число-штамп, прочитанное из хранилища эпох при входе, например 0. На каждом запросе движок открывает цепочку и одним чтением берёт из хранилища текущие штампы этих четырёх ключей. Если текущий штамп хоть одного звена больше записанного в токене, токен отозван. «Выйти на телефоне» — поднять штамп ключа «телефон»: все токены с этого телефона умирают сразу.

**Пример: как будет.** В cookie — случайные 32 байта. В базе — запись разрешения: хэш этих байт, аккаунт, тенант, устройство, родитель, срок, `revoked_at`. На каждом запросе — хэш, одна строка по первичному ключу, проверка срока и `revoked_at`. «Выйти на телефоне» — `update … set revoked_at = now() where account = 'alice' and device = 'phone'`. Отзыв уровня вместе с потомками (тенант, аккаунт, делегирование агенту) делается одной операцией по дереву в момент отзыва, поэтому проверка всегда читает одну строку.

| | Штампы (сейчас) | Запись разрешения (будет) |
|---|---|---|
| Чтений хранилища на проверку | одно (эпохи) | одно (запись) или ноль при кэше |
| Где правда о сессии | в эпохах, а с этапа 2 ещё и в записях разрешений — два места | только в записи |
| «Где я вошёл и у каких агентов есть доступ» | нельзя: штампы знают только, что отозвано, а не что существует | список записей (ASVS 3.5.1) |
| Отозвать одну сессию из многих | отдельный ключ эпохи на каждую сессию | одна строка |
| Требования к хранилищу | монотонные часы, атомарный `max(current + 1, now)`, срок ключа = максимальный срок токена, «отозвать всех» при переполнении памяти | обычная таблица |
| Отдельный порт | `EpochStore` с адаптерами памяти, Postgres, Redis и контрактными тестами | нет |

**Что теряем.** Возможностей — ничего: проверка и сейчас ходит в хранилище. Теряем только проверку из Redis без Postgres: если строка из Postgres на каждом запросе окажется дорогой, включается кэш, и отзыв доходит с задержкой до срока кэша (секунды); для агентов кэш короче или выключен. Чужим серверам штампы тоже не помогали — они не читают наше хранилище; для них, как и раньше, короткий срок токена или introspection.

### 2.3. Сервер авторизации OAuth для агентов — не писать с нуля — принято

**Было:** написать сервер авторизации самим (`/authorize`, `/token`, регистрация клиентов, метаданные, отзыв, introspection, PKCE, RFC 8707, обмен токена).

**Что не так.** Это десяток RFC с тонкими требованиями к безопасности; собственная реализация — главный источник уязвимостей в такой системе.

**Есть проверенная библиотека:** `node-oidc-provider` (автор `jose`, лицензия MIT). Реализует RFC 8707, DPoP (RFC 9449), PAR (RFC 9126), JAR, динамическую регистрацию (RFC 7591/7592), introspection, отзыв, JWT-токены доступа (RFC 9068); Client ID Metadata Documents — экспериментально. Автор сертифицировал её по профилям OpenID, включая FAPI 2.0 и CIBA.

| | За | Против |
|---|---|---|
| **`node-oidc-provider` поверх нашего движка** (хранение — через её адаптер в наши таблицы разрешений, вход и согласие — наш `signIn` и step-up, обмен токена — свой тип гранта) | Сертифицированная реализация протокола; FAPI 2.0 для финтеха АСЕАН «бесплатно»; CIBA есть | Только Node.js (не edge); один сопровождающий; её модель грантов нужно сопоставить с нашей; обмен токена (RFC 8693) дописываем сами |
| **Свой минимальный сервер только под MCP** | Работает везде; модель одна | Всё, что выше, пишем и сопровождаем сами; без сертификации |

**Рекомендую** `node-oidc-provider`, ядро движка оставить независимым от среды выполнения: сервер авторизации — отдельный пакет `@vow-auth/oauth`, который нужен только тем, кто подключает агентов и сторонние клиенты.

**Независимость от фреймворка и от среды — разные вещи.** От фреймворка `node-oidc-provider` уже не зависит: она монтируется в connect, express, fastify, hapi и koa. Зависит она от среды: только Node.js. Варианты:

| Вариант | Среда | Что есть для агентов | Чего нет | Вывод |
|---|---|---|---|---|
| `node-oidc-provider` | Node.js, любой фреймворк | RFC 8707, 7591/7592, DPoP, PAR, JAR, RFC 9068, introspection, отзыв, CIMD (экспериментально), FAPI 2.0, CIBA; сертифицирована | RFC 8693 (пишем своим типом гранта); RFC 9728 — это метаданные ресурсного сервера, отдаём сами | Берём |
| `@jmondi/oauth2-server` | Node.js ≥ 22; адаптеры Vanilla, Express, Fastify, H3 | RFC 8693, 7662, 7009, 9068, PKCE, OIDC Core и Discovery | Регистрации клиентов (7591), RFC 8707, CIMD, DPoP, PAR, RFC 8414; сертификации; один автор, около 300 звёзд | Самое трудное для MCP пришлось бы дописывать |
| Cloudflare `workers-oauth-provider` | Только Workers (KV `OAUTH_KV`, entrypoints) | OAuth 2.1, RFC 7591, 8414, 8693, 8707, 9207, 9728, CIMD, MCP 2026-07-28; токены хранятся только хэшами, данные гранта шифруются ключом, который есть только у держателя токена | Работы вне Workers; сертификации; `scope` проверяет приложение | Не берём; схему хранения заимствуем |
| OpenAuth | Hono: Node, Bun, Lambda, Workers | Свой сервер входа, `/.well-known/oauth-authorization-server` | Бета; регистрации клиентов, согласия, RFC 8707, introspection не заявлено; «в основном OAuth 2.0» | Не для агентов |
| Ory Hydra, Keycloak и подобные | Отдельный сервис (Go, Java) | Сертифицированы | Своя база и модель — второй источник правды; у Hydra, по сравнению Zuplo, нет RFC 8707 | Против инварианта |
| Свой минимальный | Любая | Ровно то, что нужно MCP | Всё пишем и проверяем сами | Запасной путь, если понадобится edge |

**Что теряем с `node-oidc-provider`:**

1. **Edge-среды** — Cloudflare Workers, Vercel Edge, Deno Deploy. Bun и Deno она не заявляет, это нужно проверять. Для первых рынков это значит немного: локализация в РФ, РК и УЗ ведёт на свои серверы в стране, где Node — обычная среда. Ядро от среды не зависит (в `core` нет импортов `node:`): вход, факторы и сессии работают где угодно, без Node остаётся только сервер авторизации для агентов.
2. **Один сопровождающий** (Filip Skokan, спонсор — Auth0 by Okta). Лицензия MIT, код зрелый; наш пакет закрывает её своим интерфейсом, так что замена не выходит за пределы `@vow-auth/oauth`.
3. **Своя модель внутри** — записи грантов, сессия сервера авторизации, cookie шага входа и согласия, хранилище «ключ → значение со сроком». Это главный риск для единого источника правды. Всё это направляем в наши записи разрешений через её адаптер и хуки (поиск аккаунта, загрузка существующего гранта), а её сессию делаем производной от нашей. Проверяется тестом: отзыв нашего разрешения сразу отзывает её токены.
4. **Обмен токена (RFC 8693)** не из коробки — свой тип гранта, свои тесты.
5. **Настройка и версии.** Настроек много; экспериментальные функции (CIMD) меняются в минорных версиях, их нужно закреплять (`~`) и подтверждать явно; поддерживается только последняя мажорная версия (v9).
6. **Вес зависимостей** — внутри Koa.

Что получаем взамен: сертифицированный протокол, FAPI 2.0 для Singpass, CIBA для этапа 7, DPoP и PAR без своей реализации.

**Можно ли взять только ядро библиотеки** (проверено по пакетам `oidc-provider` 9.13.0 и `@cloudflare/workers-oauth-provider` 1.2.4):

- **`oidc-provider` — нет.** Около 20 600 строк. Контекст Koa (`ctx`) принимают 72 из 134 файлов основных каталогов (`actions`, `models`, `helpers`, `shared`), текущий запрос хранится в `AsyncLocalStorage`, криптография — синхронный `node:crypto` (`hash`, `hkdfSync`, `KeyObject`). Отдельного ядра нет; выделить его — значит форкнуть 20 тысяч строк и потерять то, ради чего библиотеку берём: сертификацию и исправления автора. Без форка возможны Bun и Deno (они реализуют `node:http`, `node:crypto` и `AsyncLocalStorage`) — проверить прогоном её тестов в начале этапа 6; Workers — нет.
- **`workers-oauth-provider` — технически почти да.** Один файл около 6 000 строк, MIT, без зависимостей и без импортов `node:`; работает на Web `Request`/`Response` и Web Crypto. К Workers привязывают только импорт `WorkerEntrypoint` (чтобы распознать тип обработчика) и хранилище `env.OAUTH_KV` (41 вызов `get`, `put`, `delete`, `list`). Запустить вне Workers можно без форка: заглушка модуля `cloudflare:workers` и наш объект с интерфейсом KV в `env`. Но хранит она свои записи под своими ключами (`grant:<user>:<grant>`, `token:<user>:<grant>:<id>`, `client:<id>`) — это второй источник правды, а раскладка ключей — внутреннее устройство, не контракт, и может смениться в любом выпуске. В мае 2025 у неё были CVE-2025-4144 (обход PKCE, 9.8) и CVE-2025-4143 (`redirect_uri` не проверялся на `/authorize`) — исправлены, но это ровно тот класс ошибок, ради которого не пишем сервер сами. Сертификации, OIDC, FAPI, DPoP, PAR и CIBA нет.

**Вывод:** `oidc-provider` берём целиком, в Node. У `workers-oauth-provider` заимствуем схему хранения и её список спецификаций как чек-лист для MCP; она же — запасной путь, если понадобится edge.

Для входа через внешних провайдеров (Google, VK ID, Яндекс ID, Сбер ID, Singpass с FAPI 2.0) — так же: `openid-client` или `oauth4webapi` того же автора вместо своей реализации. ЕСИА с подписью ГОСТ — отдельный коннектор.

### 2.4. Passkey — фактор первого ряда

В разборе ботов вывели, что только passkey (WebAuthn) закрывает перехват кодов целиком, но в плане его не было. Добавляю отдельным этапом, вместе с телефоном (SMS и мессенджеры как каналы доставки, защита от накрутки) — без них нельзя выйти в СНГ и АСЕАН. WebAuthn — на проверенной библиотеке (`@simplewebauthn/server`), не своими руками.

### 2.5. Мелочи, которые не были записаны

- Ссылка из письма открывает страницу с кнопкой (POST), а не входит по GET: почтовые сканеры не сжигают её. Это в HTTP-слое.
- Новый токен сессии после входа и после step-up — защита от фиксации сессии (п. 2.1).
- Ключ печати записей разрешений и идентичностей выводится отдельным доменом, а не тем же, что печать значений.
- Этап 2: рассмотреть схему `workers-oauth-provider` — данные разрешения шифруются ключом, выведенным из самого токена; тогда утечка базы не раскрывает и содержимое разрешений.
- **Выбор фактора человеком (этап 5, вместе с passkey).** Сейчас политика просит ровно один фактор: `requireFactor("totp")`. Нужно, чтобы она могла предложить несколько, а человек выбрал любой из них: `requireFactor("passkey", "totp", "sms")`. Как устроить:
  - отказ step-up называет список `factors` в порядке, который предпочитает политика; приложение показывает выбор, а первый фактор может предложить сразу;
  - продолжение помнит весь список, и второй шаг принимает любой фактор из него, но не другой;
  - пройденный фактор из списка выпадает: нельзя пройти один и тот же дважды, а если все предложенные уже пройдены — отказ, как сейчас;
  - после выбранного фактора политика решает заново со всеми доказательствами: может разрешить, а может попросить ещё один из оставшихся;
  - для «хотя бы два из списка» хватает того же механизма — политика считает пройденные;
  - тест: человек проходит любой из предложенных, не может подставить непредложенный, и каждый фактор — только раз.

### 2.6. Форма продукта: открытый код и сервис на одном движке — принято

Доверие даёт открытый код, деньги — сервис.

| | Открытый код | Сервис (платно) |
|---|---|---|
| Что | Ядро, адаптеры, HTTP-слой, `@vow-auth/oauth`, сервер для своего развёртывания | Размещённый vow-auth в зонах данных (РФ, РК, УЗ, страны АСЕАН), консоль, тарифы, SLA, документы для проверок |
| Кто ставит | Разработчик: библиотекой в своё приложение или отдельным сервером | Мы |
| Как входят приложения | На том же домене — cookie напрямую; остальные — OIDC | Все — OIDC: веб через свой бэкенд (BFF), мобильные через системный браузер (RFC 8252), агенты по MCP |

Сервис работает на тех же открытых пакетах, без своей копии движка, поэтому аудит открытого кода покрывает и то, что работает в сервисе. Консоль, тарифы и управление зонами — отдельный слой поверх движка.

Следствия:

- Сервер авторизации — входная дверь сервиса, а не дополнение для агентов. Он переезжает на этап 3, сразу за разрешениями, и поглощает прежний отдельный этап JWT: токены приложениям выпускает `node-oidc-provider` (RFC 9068, внутри `jose`).
- Своё мобильное приложение входит по OIDC; отдельного «токена в заголовке» нет.
- Сессия аккаунта — непрозрачная cookie на домене входа, она же даёт единый вход между приложениями клиента, как у Auth0 и Keycloak. Это закрывает решение 1.
- **Лицензия — принято.** Движок и пакеты библиотеки открыты под MIT. Слой сервиса (консоль, тарифы, управление зонами) не публикуется. Этим снимается риск модели «деньги — сервис»: облако может запустить открытый движок, но не наш сервис; AGPL, которая отпугивает часть компаний (так сделал Zitadel в v3), не нужна.

| Что | Кому нужно | Что это значит для нас | Когда |
|---|---|---|---|
| Сертификация OpenID (OIDC, FAPI 2.0) | Банки, финтех, госсектор АСЕАН | Сертифицируется развёртывание, а не библиотека: сертификат `node-oidc-provider` к нам не переходит, каждая конечная точка — отдельное развёртывание. ## 3. Что проверено и остаётся

| Решение | Почему оставляем |
|---|---|
| Аккаунт, членства, три идентификатора, попарный `sub` | Совпадает с OIDC pairwise и требованиями локализации |
| Зона данных = развёртывание | Единственный вариант, законный для РФ, РК, УЗ |
| Факторы — плагины со своими возможностями, вход по id, привязка к провайдерам | Закрывает выпуск в обход; проверено тестами |
| `trustedProviders`, обновление данных провайдера при входе | Как у Better Auth и Auth0 |
| Политика регистрации до создания; вытеснение после разрешения | Как у Auth0 (`pre-user-registration`) и Better Auth (`databaseHooks.user.create.before`) |
| Fetch Metadata и Origin вместо CSRF-токенов; cookie `__Host-` | Рекомендация OWASP; современный подход |
| AES-GCM с ключом из HKDF на каждое значение | Без ограничения на число значений на ключ; домены разведены |
| JWT через `jose` для клиентов OAuth | Стандарт для RFC 9068 и MCP; проверенная библиотека |
| Издатель на тенанта, права агента через `scope` | Совпадает со спецификациями OAuth и MCP |
| Аудит по умолчанию не блокирует; лимиты «пара + IP» | Как у лидеров |
| TOTP с SHA-1 | Устарело только на бумаге: RFC 6238 и все приложения-аутентификаторы используют именно его |

## 4. Устаревшие подходы, от которых отказываемся

- Токены в JavaScript браузера и refresh в браузере (п. 2.1).
- Собственный механизм отзыва без серверного состояния (штампы) вместо записи сессии или introspection (п. 2.2).
- Собственное делегирование агентам вместо OAuth (уже решено).
- Собственная реализация протоколов OAuth и OIDC вместо сертифицированных библиотек (п. 2.3).

## 6. Решения

1. **Сессия:** непрозрачная сессия аккаунта вместо JWT + refresh в браузере (п. 2.1) — **принято** вместе с формой продукта (п. 2.6).
2. **Отзыв:** штампы и хранилище эпох убираем в пользу записи разрешения с необязательным кэшем (п. 2.2) — **принято**.
3. **Сервер авторизации:** `node-oidc-provider` отдельным пакетом `@vow-auth/oauth` (п. 2.3) — **принято**; с этапа 3 это входная дверь сервиса.
4. **Форма продукта:** открытый код и сервис на одном движке (п. 2.6) — **принято**.
5. **Лицензия:** движок и библиотека — MIT, слой сервиса не публикуется (п. 2.6) — **принято**.
